  1. 1

    Give the controller AWS access

    Prefer an IAM role attached to the host running the controller (an instance profile, if it's on EC2) - there's no long-lived secret to leak, since AWS rotates its credentials automatically. Attach this policy to it:

    {{ iam_policy_json }}

    The last statement (sts:AssumeRole) is only needed once you're managing a second AWS account (step 3) - delete it if you'll only ever manage this one.

    No instance role available (running locally, on your own server, or off AWS entirely)? Put an IAM user's access key in .env as AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY instead - the same policy applies to that user. Static keys are a weaker posture than a role; use them only when a role genuinely isn't an option.

    Optional: add pricing:GetProducts to this same identity to enable the dashboard's monthly cost estimates - it's public AWS catalog data, so it never needs to go on a per-account role. Without it the dashboard just shows — instead of an estimate.

  2. 2

    Get your target instances SSM-ready

    For every instance whose volumes you want managed:

    • The SSM Agent must be installed and running - it ships pre-installed on Amazon Linux 2/2023 and recent Ubuntu AMIs.
    • The instance's own IAM instance profile (not the controller's role from step 1) must include the AWS-managed policy AmazonSSMManagedInstanceCore.
    • The instance needs outbound access to the SSM endpoints (internet route, or VPC endpoints for ssm, ssmmessages, ec2messages if it's fully private).

    Nothing to check here on this page - the controller checks this automatically per instance once it's discovered, and simply skips one that isn't ready rather than failing.

  3. {% if accounts_ready %}{% else %}3{% endif %}

    Add an AWS account

    One entry per AWS account: a name you choose (permanent - it appears in every table and the audit log), an optional assume-role ARN, and the regions to scan.

    Just this one AWS account? Add it with no ARN - the controller scans the base identity's own account (the role or keys from step 1) directly.

    A second AWS account? The base identity from step 1 has to be allowed to assume a role over there:

    1. In the target account, create a role (e.g. named spaceshift) with the same policy from step 1 attached.
    2. Give that role a trust policy allowing your base identity to assume it: 
      {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::YOUR-BASE-ACCOUNT-ID:role-or-user/name" },
    "Action": "sts:AssumeRole"
  }]
}

      Find your base identity's exact ARN by running aws sts get-caller-identity with the credentials from step 1.

    3. Add the account below with that role's ARN (arn:aws:iam::TARGET-ACCOUNT-ID:role/spaceshift) and the regions to scan there.
